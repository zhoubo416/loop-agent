# 依赖管理与第三方执行代码审查

本文件定义项目第三方依赖的版本管理、普通依赖检查、执行代码审查、人工门禁、批准记录和重新审查流程。新增、升级、重新解析、安装依赖,或者修改 lockfile 或依赖声明文件前都必须先阅读;执行本流程不依赖其他规则文档补充关键步骤。

## 基本原则

- 所有依赖都要完成必要性、许可证、维护状态、公开安全信息、兼容性和版本收敛检查。
- 安装期或编译期执行代码需要更严格的专项审查;普通依赖检查不能代替执行代码审查。
- 开源仓库源码用于前置筛查,实际下载制品是判断依赖内容和执行入口的权威对象。
- 直接依赖和传递依赖采用同一套执行代码标准。
- 自动化工具可以收集证据和提出建议,但不能作出人工批准。

## 版本管理

- 版本声明的唯一来源是各子项目自己的 `package.json`（`apps/api` 与 `apps/web`），两个子项目各自的 `package-lock.json` 随改动一并提交，根目录只提供转发脚本、不维护依赖。
- 依赖版本声明用 `^` 范围,但实际安装以 lockfile 为准:lockfile 没有变化就不要重新解析(不跑 `npm update`),保证同一份 lockfile 在任何机器装出同一棵依赖树。
- 同一功能只允许一个库:新增依赖前先确认标准库或已有依赖能不能完成同样的事,发现两个库做同一件事时收敛到一个。
- npm 默认不执行第三方包的安装脚本(当前环境通过 allow-scripts 拦截并告警)。需要放开某个包的安装脚本时,按下面"执行代码审查与人工门禁"走完审查和确认,再用 `npm approve-scripts` 放行。

## 哪些代码属于执行入口

- 依赖的 `preinstall`、`install`、`postinstall` 等安装生命周期脚本,以及这些脚本调用的代码。
- 上述脚本调用的代码生成器、原生编译工具、下载器和预编译二进制。
- 项目显式运行的代码生成、编译工具和普通运行时代码按普通依赖处理;如果以后引入自动执行第三方命令的额外安装或编译脚本,按安装期和编译期执行代码的同等审查与人工批准要求处理。

## 普通依赖检查

新增或升级任何第三方依赖时,至少检查:

- 项目为什么需要它,现有依赖或标准库是否已经能够完成相同工作。
- 许可证是否允许项目使用和分发。
- 官方来源、维护组织、发布频率、维护者异常和废弃状态。
- 已公开的安全公告、漏洞、投毒和账号劫持报告。
- 与当前运行时、框架和语言版本的兼容性。
- lockfile 中的实际版本、来源和依赖图,是否引入重复版本或意外传递依赖。

没有查询到公开报告时只能写"截至检查日期未发现公开报告",不能写"确认安全"。

## 执行代码审查与人工门禁

- 安装期或编译期执行代码需要完整专项审查:先查上游源码和项目背景,再独立审查实际下载制品和完整依赖图。
- 开源仓库通过检查不能证明制品安全。实际制品包含混淆代码、预编译二进制或安装时二次下载内容时,必须尽量取得并静态检查最终内容;无法在执行前取得时,写成未消除的证据缺口,不能把供应商信誉当作源码审查已经通过。
- 最终报告至少包括:包名和准确版本、上游来源、制品清单与发布信息、实际依赖图变化和所有新增或变化的执行入口、每个入口做什么及为什么必须执行、安全信息查询结果和残余风险、准备修改的配置、首次执行和验证命令。
- 自动化工具给出最终报告后必须暂停,只有维护者看到该报告并明确确认后,才允许放行执行或首次执行。规则或历史消息里的引用、以及"同意""继续""可以"等表述都不能替代该确认。确认只对最终报告中列出的准确制品和执行入口有效。
- 批准绑定准确制品和执行入口。版本、来源、安装脚本或其调用链、安全信息发生变化时,原批准失效,需重新审批。

## 首次执行和验证

完成人工确认后,先放行对应配置,再在没有业务凭证和生产权限的环境中首次执行。验证至少包括:

- 实际网络访问、子进程、文件读写、环境变量读取和生成内容是否与静态审查一致。
- 安装或编译结果是否确实是项目需要的产物。
- 受影响项目的类型检查、测试、构建或其他必要验证是否通过。

首次执行出现未报告的行为时立即停止,撤销放行并重新进入审查流程,不能把"执行成功"视为审查通过。
